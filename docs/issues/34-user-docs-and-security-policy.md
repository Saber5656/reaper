# Title

User documentation and security policy: README, configuration reference, SECURITY.md, usage recipes

## Summary

Write the user-facing documentation set: a README that sells and explains the safety envelope honestly, a generated configuration reference, CI recipes for both modes, and SECURITY.md encoding the ADR-005 trust contract with a disclosure channel.

## Context

reaper's adoption hinges on trust; the docs must make the confidence model, the "close PR = dismiss" contract, and the security posture legible to a skeptical maintainer in minutes. Security documentation is a release blocker, not polish (DESIGN.md §17, ADR-005).

## Scope

In: `README.md` (replaces the one-line stub; keeps the Japanese tagline as a subtitle), `docs/configuration.md`, `docs/security.md` (user-facing) + `SECURITY.md` (root, disclosure policy), `docs/recipes.md`, CONTRIBUTING.md stub.
Out: code changes (docs-only except a tiny schema-to-markdown script), marketplace copy (35).

## Detailed Requirements

1. `README.md` structure (English, tagline bilingual):
   - What it does in 5 lines + a real PR screenshot (from 33's dry-run body or a live run).
   - "How it decides" — the §10/§11 model in one table + one worked example (§10.6#2) including *why the false positive was caught*.
   - Quickstart: local (`npm i -g …` placeholder name → `reaper init && reaper doctor && reaper scan`) and Action (report-mode YAML, then propose-mode YAML with permissions + trigger warning).
   - Capability matrix (§9.2) verbatim — honest about report-only cells.
   - The contract bullets: close-PR-to-dismiss, `reaper-keep`, protect globs, budgets, verify gate.
   - Comparison section (§1.1 table) naming knip/vulture/deadcode as engines, not competitors.
2. `docs/configuration.md`: generated by a small script (`pnpm docs:config`) walking `schema/reaper-config.schema.json` descriptions (03) into a reference table (key, type, default, description, safety floors called out); CI check that it is regeneration-clean (drift fails).
3. `docs/security.md` (user-facing model): trust contract in plain words ("running reaper on a ref executes that ref's dev tooling — treat it like running its tests"); token guidance (minimal permissions blocks per mode); trigger guidance (schedule/dispatch; why fork-PR propose is refused); what reaper never does (auto-install, force-push, auto-merge, telemetry).
4. Root `SECURITY.md`: supported versions table, private disclosure via GitHub Security Advisories, response-time commitment (e.g. 14 days triage), scope notes (what counts: envelope bypasses — a trap-class finding that gets proposed IS a security bug; report it as one).
5. `docs/recipes.md`: scheduled propose; report-only PR gate with `--fail-on high`; monorepo `working-directory`; local pre-release audit; suppressing false positives walkthrough (annotation → protect → close-PR, when to use which).
6. CONTRIBUTING.md stub: dev setup, test commands incl. `test:e2e`, golden-refresh flow (33), "changing a confidence weight requires a fixture case" rule (ADR-003).
7. Cross-checks: every CLI flag in docs exists in `--help` output (scripted check `pnpm docs:check` diffing commander metadata vs documented flags); every config key documented (schema walk guarantees).

## Acceptance Criteria

- [ ] README covers all listed sections; a newcomer path (install → doctor → scan → first PR) is followable without reading DESIGN.md.
- [ ] `docs:config` regeneration-clean check wired into CI; flag-coverage `docs:check` green.
- [ ] SECURITY.md names the advisory channel and classifies envelope bypasses as vulnerabilities.
- [ ] Security docs match implemented guards exactly (cross-review against 32's error messages — no doc/behavior drift).
- [ ] All docs in English; Japanese tagline preserved in README header.

## Validation

`pnpm docs:config && git diff --exit-code`; `pnpm docs:check`; prose review pass recorded in the PR.
